## Deliverable guarantee

On the specified personal device the owner can resume the specified usual work with intended tools/settings, actual required files/application state at approved state/versions, and permitted usable identities. Approved retrieval/restoration/retention and supported identity re-establishment work with independently available bootstrap where needed. Missing or wrong-version material reports not ready; references do not recreate lost data.

Software-only or populated-directory completion is not the seed. No blanket credential clone, unrelated data authority, universal VPN enrollment, personal recovery-point target or cloud/source product is chosen. Existing platform differences may be intentional. Real usable work/state/identity behavior must be exercised with the relevant native VM/live/platform evidence, not only configuration evaluation.

## Accepted decisions

### Complete standalone guarantees instead of partial setup

- Context: the adopted six actor-goal contracts require complete application/data/recovery/work outcomes. Initial setup or restoration of a route does not cover a deliberate existing-application path change. The user adopted the four-deliverable Handoff cut (Q18).
- Options:
  1. **Adopt the six-leaf/four-guarantee cut** — each goal keeps its own permanent leaf and each seed delivers an end-to-end result with true/conditional dependencies.
     In practice: a photo app without a usable required recovery point and an editor without required working state are unfinished; a passive path flag is not a completed reachability change.
     Gain: independently shippable results without silent uncovered goals or config-only completion.
     Cost: each real target, procedure, source and meaningful proof must be supplied; this is not a universal platform shipped by one settings change.
  2. **Revise a named delivery boundary first** — regroup a complete guarantee while preserving the accepted rules.
     In practice: photo hosting may be the first real recovery target in a merged guarantee, rather than forcing a generic empty backup fixture first.
     Gain: better fit for the desired first actual target.
     Cost: revisit affected coverage/dependencies before implementation; no intermediate state may violate readiness/protection.
- Chosen: **Adopt the six-leaf/four-guarantee cut** because the user explicitly said "Adopt this cut". Rejected: revising a named boundary first because the displayed cut was accepted. This is an approved seed boundary, not product/source selection, deployment, release-order commitment or automatic change start.

### Complete usable working environment including required personal state

- Context: the user named reproducing the usual working environment as the device goal (Q7), placed VPN under applications, and then chose required personal-state-inclusive readiness (Q15).
- Options:
  1. **Usable environment including required state** — required working files/app state and permitted identities must be available or re-established before readiness is claimed.
     In practice: the owner resumes the intended project with its required files and resource access, not merely an editor launcher.
     Gain: end-to-end work readiness.
     Cost: identify approved state/source/version requirements and safe independent bootstrap; configuration alone does not supply them.
  2. **Software/settings with state supplied outside this goal** — reproduce tools/settings while working files/identities come from a separate workflow.
     In practice: the configured editor starts, but the project files or identity must still be supplied elsewhere.
     Gain: bounded configuration setup.
     Cost: cannot alone promise the usable workspace the user selected.
- Chosen: **Usable environment including required state** because the user explicitly selected that outcome. Rejected: software/settings-only completion. VPN remains a requirement of selected apps when needed, not a universal base goal; no numeric personal-data tolerance or indiscriminate key copying follows.

## Open questions

### Approved required state and identity sources (Q16)

What owner-approved source supplies each actual required working-state/identity item on the chosen device, at which required state/version/point, and with which independently usable bootstrap? This inventory blocks implementation/proof, not the full readiness guarantee. Tracked profiles identify local workspace/app/credential paths and sync clients, but declarations do not prove surviving copies, current authentication or external escrow; private/out-of-repo arrangements were not audited. State may already be present or come from authoritative storage/suitable supported restore. Bind real inputs; do not reconstruct missing uncommitted work from a clean checkout or lost private keys from path references.

### Supported platform/application state handling

Which selected state formats and identity procedures can be retrieved/restored/re-established on the intended platform without silently overwriting required work or exporting hardware-bound credentials? This is a technical/operating input under the accepted goal. Current macOS/Linux profiles differ; ordinary home persistence on macOS is not a defect by itself, and same-device Linux persistence is not off-device recovery proof. Preserve permitted scope and explicitly report unsupported or missing material.
