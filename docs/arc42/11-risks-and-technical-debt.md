# 11. Risks and Technical Debt

Known risks and technical debt that affect the architecture or the ability to
trust this documentation. Each item is evidenced; probability/impact are
qualitative.

## Risks

| ID | Risk | Probability | Impact | Mitigation |
|---|---|---|---|---|
| R-001 | A declared personal identity file is absent on the device (stale path after a key rotation, or key removed) | Medium | Medium | The declaration is proven on the device after activation: `ssh -G <connection>` must name an existing key file, and a private-repository `git fetch` must succeed. Failure is fail-closed: no key is presented and access is denied, never broadened. |
| R-002 | A host declares a work identity's secret material without holding that identity's key file, so it renders a connection entry it cannot use | Low | Low | The same declaration gates both the connection entry and the workspace identity profile, so the two cannot drift apart; a missing key still fails closed. |
| R-003 | A second work device inherits the MacBook's work identity surface if it declares the same secret material with different key files | Low | Medium | Accepted for now: no second work device exists. Tracked as TD-001 with the parameterization that removes it. |
| R-004 | Documentation drift: `docs/ARCHITECTURE.md` and `CLAUDE.md` describe hosts and files that do not exist (`pronix`, `*-vm` configurations, `hosts/cupix001/networking.nix`, `hosts/cupix001/headscale.nix`, `features/linux/impermanence.nix`, `tests/deploy/`, `docs/EDGE-INGRESS-GATEWAY.md`) | High | Medium | This arc42 baseline is the corrected account. Fixing the stale prose is tracked as TD-005; until then, treat those two files as historical. |
| R-005 | `scripts/netcup_firewall.py`, `infra/firewall/*` and the netcup CLI help still document an `apply` subcommand that no longer exists in the parser | High | Low | The parser is authoritative; `.http` collections and the plan files still describe the same shape. Tracked as TD-004. |
| R-006 | `hosts/thiniel/default.nix` depends on the systemd initrd implementation introduced in 26.05, while the previous scripted-stage-1 form is removed in nixpkgs 26.11 | Medium | Medium | The systemd form is already in place and guarded by `tests/assertions/thiniel-boot-invariants.nix`; the risk is an unnoticed reversion during a future channel upgrade. Re-verify on the 26.11 upgrade. |
| R-007 | `.sops.yaml` binds `adlerkopf` and `cupix001` to the **same** age recipient value, so a copy of one host's key can decrypt the other host's secrets | Medium | Medium | None recorded. Whether this is intentional (e.g. derived from a shared key) is unknown; it must be confirmed before adding secrets. |
| R-008 | A host's real operational values come from the `private` flake input; a deploy that omits `--override-input` evaluates the in-tree stub, which is indistinguishable from a clean-clone evaluation | Medium | High — a placeholder address applied to a host can lock out SSH | The deploy path carries a preflight (the per-host rebuild alias) that refuses to deploy when the override supplied no values; a wrong value that removes SSH is recovered out of band (adlerkopf's local systemd-boot menu). The stub assertion guards the defaults, not the forgotten override ([ADR-0001](adr/ADR-0001-private-data-strategy.md)). |
| R-015 | Adding a host now requires touching two repositories (the stub module in the public one, the real module in the private one), so the two can drift | Medium | Low | The `private-data-hygiene` check and the README's host-addition sequence name both sides; the friction is intentional ([ADR-0001](adr/ADR-0001-private-data-strategy.md)). |
| R-016 | The repository's history still records the operational values until the one-time rewrite runs, and a public GitHub clone keeps old objects for a period after the rewrite | High | High | The rewrite is a task of the change `private-data-remediation` and is guarded by a mirror-clone backup; every value already recorded is treated as disclosed, and the operational responses (new address, token rotation, host keys) are tracked separately. |
| R-017 | `nixosConfigurations.adlerkopf`'s toplevel did not evaluate: `boot.initrd.luks.devices.cryptroot.device` had conflicting definitions — disko's `disk-nvme0n1-cryptroot` against `hosts/adlerkopf/tpm2.nix`'s `cryptroot` | High | High — the canonical `@host:adlerkopf` targeted command could not exit 0, and a real `nixos-rebuild` of that host could not build | **Fixed** by preserving the adlerkopf branch work (`worktree/roo-f8e9n`'s `f8dd195`, whose `flake.nix` half was already in `main` but whose `tpm2.nix` half was not): the stale `device` line is removed and disko's value stands. `nix eval .#nixosConfigurations.adlerkopf.config.system.build.toplevel.drvPath` now exits 0. |
| R-009 | `cupix001` is declared with the role "edge gateway" (README/`CLAUDE.md`/plans/docs) but is a services-free skeleton; the operator may believe the gateway exists | Medium | Medium | The gateway is a **confirmed future effort** (sequenced after the private-data remediation that must precede a public release), not a current capability; [chapter 7](07-deployment-view.md) states the skeleton explicitly. Tracked as TD-006. |
| R-010 | `networking.cupix001.*` is declared but consumed by no module, so setting any of its thirteen values has no effect | Medium | Low | Tracked as TD-002. The values have effect only once a networking module reads them. |
| R-011 | `modules/nixos/persistence` is imported by `cupix001` while `mySystem.persistence.enable` is never set, so the persistence block is inert although `disko` mounts `/persist` | Medium | Low | Tracked as TD-003. Enabling it is a one-line host change. |
| R-012 | The `nixpkgs` 26.11 upgrade may break more than the thiniel wipe: `adlerkopf` uses LUKS + TPM2 + lanzaboote, and `nixos-vm-minimal` uses disko + LUKS, all of which follow the pinned channel | Low | High | Follow the channel deliberately (`docs/plans/upgrade-26.05-plan.md` is the precedent); rebuild each host generation before switching. |
| R-013 | The VM integration tests (and therefore every `@e2e` scenario) require a Linux builder with KVM; on the Darwin workstation they fail loudly rather than silently pass | Medium | Low | By design (`scripts/givn-verify-e2e.sh`); run the e2e scope from a Linux host or `nix.linux-builder`. |
| R-014 | `flake.lock` currently has uncommitted changes, so the reviewed configuration and the pinned revision in the working tree differ | Low | Medium | Commit or discard the lock update; the change is unrelated to this baseline. |
| R-018 | The coding agent's source pin goes stale between deliberate refreshes, so the devices silently fall behind the floor's intent (upstream cuts several releases per day) | High | Low | The pin is refreshed deliberately (`nix flake update nixpkgs-agent`); the floor assertion keeps a regression visible, and [chapter 10](10-quality-requirements.md) QS-014 states that a schedule is deliberately not promised. |
| R-019 | The agent's pin follows `nixpkgs` master, so a refresh can bring an unreviewed upstream change to both devices at once | Medium | Medium | Refreshing is a deliberate owner action, not automatic; the floor assertions plus the `integration-agent-tooling` VM check catch a broken Linux build, and the Mac is confirmed at activation. |
| R-020 | The `unit-agent-secret-guard` check mirrors the agent's hook event shape (`toolName` in `read`/`grep`/`bash`/`eval`); an agent release that changes that shape could pass the check while no longer refusing real calls | Low | High — a silent hole in the decryption prohibition | The driver mirrors the hook's own dispatch and the hook is the tracked project hook; a refusal inside a live session remains unverifiable without a model provider, so the coupling is recorded here rather than mitigated. |
| R-021 | The agent's secret-access guard denies a fixed glob set (`/run/secrets/*`, a `sops/age/` path, `/var/lib/sops-nix/*`), so a *direct* `read` of a user-side sops-nix secret (`~/.config/sops-nix/secrets/…`, where this repository's `context7` and `kagi` keys sit) is not refused by the guard | Low | Low | **Operator decision (2026-10-13): accepted, no guard change.** Those keys must stay at that path — it is where the sops-nix home module places them — and the agent does not receive key material in normal use: the MCP declaration's `!command` indirection is resolved by the MCP plugin (the client side of the connection), not by the agent's tools, so the model never sees the value. The residual property is that a session which *deliberately* asks the agent to read that path is not blocked by the guard; the process rule in `CLAUDE.md` and review of what a session is asked to do cover that case. |

## Technical debt

| ID | Item | Impact | Plan to address |
|---|---|---|---|
| TD-001 | The three work identity key file names remain literals inside `home/dan/features/cli/ssh.nix`, gated by declared secret material rather than declared per host the way the personal identity is | A second work device would render the MacBook's key paths and fail closed | Parameterize the work identity key paths in `myHome.ssh` when a second host needs them |
| TD-002 | `hosts/cupix001/options.nix` declares thirteen `networking.cupix001.*` options that no module consumes | Dead declarations: they look like configuration but control nothing | Add the networking module that reads them, or remove the option set |
| TD-003 | `modules/nixos/persistence` is imported by `cupix001` with the enable flag unset | The persistence block never applies although disko mounts `/persist` | Set `mySystem.persistence.enable = true` when cupix001 becomes a real host |
| TD-004 | `scripts/README.md`, the module docstring and parts of `infra/firewall/README.md` still document a removed `apply` subcommand | An operator following the docs runs a command that does not exist | Update both to the current subcommand set (`backup`, `lockdown`, `restore`, `ssh-open`, `ssh-close`, `openapi`, `server`, `policy`, `tasks`) |
| TD-005 | `docs/ARCHITECTURE.md` and `CLAUDE.md` carry a stale host/feature inventory (`pronix`, `*-vm` configs, removed files, `tests/deploy/`) | Misleads readers and agents about what exists | Reconcile with the fleet in [chapter 7](07-deployment-view.md); keep `CLAUDE.md` as process guidance only |
| TD-006 | `cupix001` is a skeleton; `docs/edge-all.md` and the cupix001 plan set describe an ingress/VPN stack (Caddy forward-auth, WireGuard, derper, CrowdSec, nftables, Authentik) that does not exist | A confirmed future effort, so the gap is expected — but the role labels in `README.md`/`CLAUDE.md` still read as if it were running | Start the cupix001 phases after the private-data remediation lands; until then keep the plan set marked unstarted |
| TD-007 | `tests/deploy/` (pytest-testinfra) is documented in `CLAUDE.md` and `docs/GIVN-VERIFICATION.md` but absent, so the `@deploy:` binding tag cannot resolve | A scenario may be bound to a target that does not exist | Remove the `@deploy:` tag from the policy or add the deploy layer |
| TD-008 | thiniel defers automated versioned backups in code (`TODO(2026-04)` in `hosts/thiniel/default.nix`); the restic plan on adlerkopf has no confirmed target; the ideation 24-hour point is unimplemented | QS-012/QS-013 cannot be satisfied; personal data-loss windows are undefined | Decide a source/destination/retention, then implement a declared backup job; the photo target is a planning baseline, not a universal one |
| TD-009 | Modules reachable from no host profile: `features/productivity/emacs.nix`, `features/productivity/vscode.nix`, `features/cli/zsh.nix`, `features/development/jdk.nix`; `features/linux/impermanence.nix` referenced by `CLAUDE.md` does not exist | Dead modules and a broken doc reference; a reader cannot tell whether they are intentional alternatives or leftovers | Delete or wire each deliberately; delete the stale reference |
| TD-010 | `colmena` is an input, a dev-shell package, a host alias (`cs`/`ct`/`cb`/`cda`/`call`) and a flake output, but `colmenaHive` registers no nodes | An aliased tool that cannot act on any host | Register nodes when coordinated deployment starts, or drop the aliases |
| TD-011 | `adlerkopf/default.nix` declares a `virtualisation.vmVariant` block with `adlerkopf.vmMode = true`, but no flake attribute materializes it and the `integration-adlerkopf` check boot-tests a synthetic machine instead | The VM-mode escape hatch for adlerkopf's hardware assertions is unreachable dead configuration | Either expose the variant as a configuration and boot it, or remove the block and the `vmMode` guards in `tests/assertions/adlerkopf-invariants.nix` |
| TD-012 | `packages.default.mcp-nixos` and `devShells` name systems explicitly; the Colmena `meta.nixpkgs` comment advertises a per-node override that no node uses | Small duplication that drifts when the system list changes | Revisit when the system list changes |
| TD-013 | The `pkgs/` directory is a placeholder and `scripts/*.sh` are not derived packages; the README's "Scripts migration to Nix derivations" remains open | Deployment scripts are outside the flake's build graph and its checks | Migrate when the scripts stabilize, or state that they stay shell |
